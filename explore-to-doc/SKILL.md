# 三种记忆，分开落档

这是**三套记忆**，不是同一类笔记换目录：

| 记忆 | 含义 | 目录 | 索引 |
|------|------|------|------|
| 常规项目探索 | 跨仓架构、模块怎么工作、以后还要当依据 | `docs/` | 更新 `docs/index.md` 的探索表 |
| 设计 / 架构 | 从 agent 对话抽出的设计决策、架构结论、方案取舍 | `docs/design/` | 更新 `docs/index.md` 的「设计 / 架构」小节 |
| 临时 review | 某次 review / 缺陷清单的核对、改了什么、测了什么 | `docs/tmp/` | **禁止**写入 `docs/index.md` |

不要写进子仓库自己的 `docs/`（如 `codely-cli/docs/`、`unity-insight/docs/`），除非用户明确指定。用户指定其它路径时从其指定。

**禁止混写：**

- 不要把临时 review 写进 `docs/` 根下的探索文档（只写 `docs/tmp/`）。
- 不要把架构结论、模块说明只写在 `docs/tmp/`。
- 不要把对话里抽出的设计/架构写进 `docs/` 根下或 `docs/tmp/`（只写 `docs/design/`）。
- 不要把探索路径、review 核对写进 `docs/design/`。
- 不要在 `docs/index.md` 里挂 tmp 条目；也不要把 design 条目混进探索表。
- 临时记录里的发现若要变成项目依据：另写一份探索文档到 `docs/`，不要把 review 全文搬过去。
- 对话里的设计若已有对应探索文档：互链，不要把探索全文搬进 design，也不要把设计决策只留在探索文档里。

文件名均为 `YYYY-MM-DD-<简短主题kebab-case>.md`。同日同主题已有文件则更新，不另起散文件。`docs/design/` 在首次落档时创建，无需占位文件。

## 何时启用

**项目探索**（`docs/`）满足任一即启用：

- 为回答问题需要搜索/阅读 **≥5 个文件**，或跨越 **≥2 个目录/模块**
- 探索路径出现分支（多处候选、多次排除、对比方案）
- 结论依赖链路追溯（调用链、配置来源、数据流）
- 用户明确要求「整理探索过程 / 写入 docs / 记录排查过程」

**设计 / 架构**（`docs/design/`）满足任一即启用：

- 正在阅读 agent 对话 / transcript / 历史会话，并从中得到设计决策、架构结论、模块边界、协议/数据流、被否决方案
- 用户明确要求「写入 design / 沉淀设计 / 记录架构决策」

阅读对话时一旦抽出**可独立复用**的设计/架构，立刻落档，不要等用户再要求。只记稳定结论与取舍，不记聊天过程；过程性排查仍按探索或 tmp 分流。

**临时 review**（`docs/tmp/`）满足任一即启用：

- 用户要求「整理修复过程 / 写到 tmp / 记录 review」
- 已按某次 review 或缺陷清单改完，只需留下核对与结果

简短跟进、单文件小改、已知路径的直接编辑：**不启用**。

## 落档时机

1. **探索中途**：关键发现已成型、但任务尚未结束 → 先写/更新 `docs/`，再继续实现。
2. **探索结束**：已得出可用结论、准备交付答案或动手改代码之前 → 必须落档到 `docs/`。
3. **阅读 agent 对话**：抽出可复用的设计/架构 → 写/更新 `docs/design/`，并更新 `docs/index.md` 的「设计 / 架构」小节。
4. **临时 review 落地后**：对照清单核对已改与未改，写 `docs/tmp/`。
5. **同一主题续写**：探索追加「续探」；设计更新同一 `docs/design/` 文件；临时 review 更新同一文件。勿把一类记忆续写到另一目录。

## 探索文档结构（`docs/`）

```markdown
# <探索主题>

- 日期：YYYY-MM-DD
- 问题：<用户原问题的一句话复述>
- 状态：进行中 | 已结论

## 目标
<本次探索要回答什么>

## 探索路径
1. <做了什么> → <关键线索 / 排除项>
2. ...

## 关键发现
- **<发现>**：依据（路径、符号、行为）
- ...

## 结论
<可执行结论；不确定处明确标注>

## 仍开放的问题
- <可选；无则写「无」>

## 相关路径
- `path/to/file` — 简述角色
```

## 设计 / 架构格式（`docs/design/`）

只沉淀对话里已经说清的决策与结构，不要把 transcript 全文搬过来。来源会话能定位时写上标题与 id。

```markdown
# <设计 / 架构主题>

- 日期：YYYY-MM-DD
- 来源：agent 对话
- 状态：草案 | 已确认
- 问题：<一句话：这段对话在定什么设计/架构>

## 背景
<要解决的设计问题与约束>

## 决策
- **<决策>**：依据（对话结论、对比、约束）

## 架构
<模块边界、数据流、协议、职责；不确定处标注>

## 否决方案
- <方案>：否决原因（无则写「无」）

## 相关路径
- `path` — 角色

## 来源会话
- [<会话标题>](<transcript-id>) — 抽了哪些结论
```

- 同主题已有 `docs/design/` 文件则更新，不另起散文件。
- 与探索文档互补：探索记「怎么查到的」，design 记「最后定了什么」。

## 临时 review 格式（`docs/tmp/`）

记录文件的格式类似 skill，分为头和内容。头用一句话描述问题和解决思路，内容则是详细内容。

```markdown
---
name: <kebab-case-主题>
description: <一句话：问题是什么，以及解决思路>
---

# <主题>

## 核对

- <review / 缺陷项> → 属实 | 树里已有 | 不成立；处理：已修 | 不改 | 仍开放

## 过程

1. <做了什么> → <线索 / 排除 / 失败原因>
2. ...

## 改动

- `path` — 改了什么、为什么

## 验证

- <命令>：结果
- 未跑：<列出>

## 仍开放

- <无则写「无」>
```

- `name`：小写字母、数字、连字符，与文件名主题段一致。
- `description`：**一句话**同时写清问题和解决思路，不要拆成两段，不要在头里写步骤或表格。

## 写作要求

- 记「过程与依据」或「决策与取舍」，不是聊天记录全文；不粘贴大段无关代码
- 路径用仓库相对路径；结论与证据对应
- 失败尝试与排除项要写清，避免后人重复踩坑
- 落档后在回复中告知用户：文档路径 + 一句话摘要（临时 review 可复用头里的 `description`）

## 与其它技能的关系

- `memwalker`：长材料交互式阅读（摘要树 + 导航）→ `.memwalker/` 等；从对话/长文抽出的设计结论仍写 `docs/design/`
- `auto-summary-context`：会话 context 过高时压缩对话历史
- 本技能只负责落档位置与格式；三套记忆仍分开，不互相替代
