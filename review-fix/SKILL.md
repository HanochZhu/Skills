# Review Fix

按 review 修代码时，顺序不能反：

1. **优先检查 review 的内容是否正确符合当前的现状**
2. **编写测试，先复现 review 中说的问题**
3. **复现成功之后再进行修复，以通过测试为目标**

未核对或未复现成功的条目，不改生产代码。

## 何时启用

- 用户要按 review / Bugbot / MR / PR 评论 / 缺陷清单改代码
- 用户说「复现再修」「先写测试再修」

不要用于：只要评、不要改（走 review 类 skill）；从零做新功能；纯文案/重命名且用户只要改字。

## 工作流

复制并勾选。每条 finding **独立**走完 1→4，再下一条。

```
Review fix:
- [ ] 0. 拆条（声称 / 期望 / 位置 / 严重度）
- [ ] 1. 核实现状 → 属实才继续
- [ ] 2. 写测试（断言期望行为，尚未改生产代码）
- [ ] 3. 跑测试：因该问题失败（RED）
- [ ] 4. 最小修复，使该测试通过（GREEN）
- [ ] 5. 邻近回归 + 收尾
```

默认只处理**属实的缺陷**。建议 / nits / 风格：用户点名或明确「全部处理」才做。

### 0. 拆条

把 review 拆成互不粘连的条目。每条记下：

| 项 | 要写清 |
|----|--------|
| 位置 | 文件 + 符号；行号只当线索 |
| 声称 | review 说现在怎样 |
| 期望 | review 说应该怎样 |
| 严重度 | 缺陷 / 建议 / nit |

按严重度高的先做。不要先改 nits。

改**实际源码仓**，不要改 submodule 拷贝或另一份克隆。

### 1. 核实现状（必须先做）

对照的是**当前工作区**（HEAD / 未提交改动），不是 reviewer 当时的快照。

- 打开声称的文件与符号；行号过期就按符号重定位
- 读现有测试：是否已覆盖、是否把「错误行为」锁成契约
- 有设计/探索文档则对照：当前行为若是已确认设计，标「不成立」
- 判定只能是下面之一：

| 判定 | 含义 | 下一步 |
|------|------|--------|
| 属实 | 现状仍是声称的问题 | 进入写测试 |
| 已修 | 树里已经没有该问题 | 记录，不改 |
| 不成立 | 误读、行号错、或与已确认设计冲突 | 说明依据，不改 |
| 过期 | 相关代码已换，评论不再适用 | 说明现状，不改 |
| 超出范围 | 要另开需求 / 大重构 | 停下来问用户 |
| 建议 | 非缺陷 | 默认不改 |

禁止：跳过核对直接改；为「不成立」的评论写测试去锁错误期望。

### 2. 编写测试，先复现

只对「属实」条目写测试。**此时还不许改生产代码。**

- 断言**核对后的期望行为**（修好之后该怎样），不是把 bug 写成合法结果
- 沿用项目已有 runner 与邻近测试文件；不要新开框架
- 用能打到出问题那一层的最小测试；不要 mock 掉出 bug 的路径
- 一条 finding 一个测试（或一个 `describe`）
- 不要 `skip` / `xit` / 注释掉断言
- 已有测试锁住了错误契约：先把那些断言改成期望行为，让它们变红，再进入修复

测不了（纯命名、纯文档）：写明「无测试」，不要编假测试。竞态 / UI / 时序：用最接近的确定性代理。仍写不出：问用户是否允许无测试就改；**默认不允许**。

安全类评论：只写「拒绝不安全输入 / 保持安全行为」的测试。不要写 exploit、攻击 PoC、未授权访问步骤。

### 3. 确认复现成功（RED 闸门）

必须跑测试。复现成功 = **失败，且失败原因就是这条 review 说的问题**。

| 结果 | 做法 |
|------|------|
| 断言失败，原因对得上 | 复现成功 → 才许改生产代码 |
| 立刻通过 | 不属实或已修；停止，不要再「修」 |
| 报错（语法/装配/路径） | 只修测试 harness，重跑到真正的 RED |
| 失败原因不对 | 改测试，不要改生产代码 |
| 多次仍无法复现 | 记录「无法复现」并停止；禁止猜着改 |

没看到正确的 RED，等于没有复现。

### 4. 复现成功之后再修复

目标：让**第 2 步那条测试**通过。

- 只做最小改动；不顺手重构、不扩 scope、不顺带改相邻模块
- 禁止为了绿灯削弱、跳过或改写第 2 步的断言
- 测试仍红：改生产代码，不要改测试
- 其它已有测试红了：先分清是合法回归还是误伤；误伤就修实现，不要删旧测试

### 5. 回归与收尾

- 新测试 + 同一文件 / 邻近套件都要绿
- 改了 Web UI：在浏览器里走一遍受影响路径，不只看截图
- 有 `explore-to-doc` 且用户要留记录：写 `docs/tmp/`，不要写进探索/design
- 未要求则不 commit、不 push

## 多条与停止

- 每条独立：核对 → RED → 修复 → GREEN，再下一条
- 不要先改完一堆，再补一个大测试
- 一条无法复现：跳过它，不要连累其它属实条目
- 用户只点了部分条目：只做点名的

遇到这些立刻停那一条：现状对不上、无法复现、与已确认设计冲突、需要大范围重写。

## 反模式

- 先改代码再补测试（测试立刻绿，证明不了抓住了问题）
- 未核对行号/文件就开改
- mock 掉出问题的那一层还声称「复现了」
- 复现失败仍「按 review 改一把」
- 为通过而改断言、跳过测试、删旧测试
- 把建议当成缺陷，或顺手重构半个模块
- 写攻击 PoC 当安全复现

## 回复格式

先给核对表，再写改了什么、跑了什么：

```markdown
| 条目 | 判定 | 处理 |
|------|------|------|
| <file:symbol / 原评论一句> | 属实 / 已修 / 不成立 / 过期 / 无法复现 | 已修 / 不改 / 仍开放 |
```

验证写实际命令与结果。未跑的列出。

## 与其它技能

| 技能 | 关系 |
|------|------|
| `explore-to-doc` | 一次性核对/修复过程可写 `docs/tmp/`；不要写进探索或 design |
| 项目内 TDD skill | 本 skill 多了「先核 review 是否属实」；属实之后的红绿循环与 TDD 一致 |
| `review-bugbot` / `review-security` | 只出 finding；用户要求修时再转本 skill |
